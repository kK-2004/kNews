## Context

本次 change 不是新增一块全新的前端功能，而是把已经在 renderer 侧连续落地的一组 UI polish 回填为正式设计与规格。涉及模块横跨 `App.vue`、首页 source board、K-Ai 助手页面、settings 侧栏、后台分析卡片和全局主题变量，因此需要用一个跨模块设计文档明确边界和决策。

当前项目的几个重要约束如下：
- 已有前后端逻辑已经可用，本次不得因为美化而改动后端接口、权限模型或聊天流式协议。
- K-Ai 助手当前仍是“全局单流”架构，前端只能在这个前提下补保护与提示，不能在本次 change 中偷渡成多会话并发流。
- 全局主题已经切换为 CSS 变量驱动，适合继续通过 renderer 样式层统一黑白主题与局部来源色点缀。
- 首页、助手、设置页的诉求来自同一轮设计迭代，如果不统一沉淀到 spec，后续很容易再次出现样式回摆或行为漂移。

## Goals / Non-Goals

**Goals:**
- 以不改后端逻辑为前提，正式定义这一轮首页、助手、设置/后台和全局导航的 UI/交互约束。
- 让黑白主题、中文界面、active 样式、按钮布局和占位状态形成统一规则，而不是分散在零散提交中。
- 把 K-Ai 助手在当前单流架构下的用户可见行为固定下来，避免后续误以为支持多会话并发流。

**Non-Goals:**
- 不引入新的 UI 框架、主题系统或状态管理模式。
- 不修改聊天 IPC、MCP 接口、权限逻辑或 API 数据结构。
- 不把本次 polish 扩展成新的后端能力开发，例如多会话并发流、排行榜新接口或新的订阅权限模型。

## Decisions

### D1. 全局外壳继续使用黑白主基调，仅允许局部来源色点缀

**选择**: 全局壳层、导航、设置和基础消息气泡继续以黑白灰 CSS 变量为主；首页卡片、K-Ai 热点序号等局部元素允许读取来源配置色做轻量点缀。

**理由**:
- 用户明确要求适配黑白主题，但又希望首页卡片保留数据源识别度。
- 以“黑白主基调 + 来源色局部点缀”的方式，能兼顾统一性和信息辨识度。

**备选方案**:
- 完全移除所有来源色，只保留纯黑白。
  放弃原因：来源识别度下降，首页和热点卡片的信息层次会变弱。

### D2. 首页切换性能问题通过前端即时加载态和请求保护解决

**选择**: 首页 tab 切换时立即清空当前板块展示并进入骨架屏或等价加载态；同时保留请求序号或同等保护，避免旧请求覆盖新 tab。

**理由**:
- 用户反馈的卡顿感来自“切换后长时间停留旧内容，骨架屏出现太晚”，核心是前端状态时机，而不是后端接口设计。
- 该方案不改接口，且对现有缓存优先策略兼容性最好。

**备选方案**:
- 重写首页数据加载协议或强制每次切换都等待新请求完成。
  放弃原因：成本高，且会破坏现有缓存优先加载逻辑。

### D3. K-Ai 助手继续沿用单流架构，通过前端约束显式化

**选择**: 既然当前 store / IPC / chat service 都是单个活跃流模型，本次不改架构，只在前端对发送、新建、切换、删除等入口统一拦截，并显示固定错误提示。

**理由**:
- 用户明确说明“暂时使用现在的全局流”。
- 这能把当前真实能力准确传达给用户，避免出现“没有提示但也没响应”的假死体验。

**备选方案**:
- 在本次 polish 中顺带改造成多会话并发流。
  放弃原因：超出本次 change 范围，也会触及后端逻辑与 IPC 契约。

### D4. 设置与后台模块优先保证状态可见，而不是空白等待

**选择**: 设置页导航选中态、深色模式开关、后台排行榜等模块统一以“高可见 active + 明确 loading/empty state”为目标，避免深色看不见或整块留白。

**理由**:
- 用户本轮反馈集中在“看不清”和“空一块”，说明主要问题是状态可见性而非数据能力。
- 这些问题都可以通过 renderer 层样式和占位处理解决。

**备选方案**:
- 保持当前布局，只依赖 hover 或数据返回后再显示。
  放弃原因：不能解决深色模式可见性和预加载空白问题。

### D5. 规格文档按“已落地实现”回填，tasks 以完成态记录

**选择**: 由于本轮大多数改动已经实现，OpenSpec tasks 使用已完成状态回填，而不是伪装成尚未开始的待办。

**理由**:
- 这样更符合代码现状，也便于后续 archive 或继续扩展。
- 避免出现“代码已改完，但规格里仍全是未完成任务”的文档失真。

## Risks / Trade-offs

- **[规格回填滞后于实现]** → 通过把任务写成已完成态，并同步更新 SRS，减少规格与代码不一致窗口。
- **[黑白主题过于单调]** → 保留来源色点缀，仅在来源相关信息上使用，不让页面完全失去层次。
- **[单流限制被误解为 bug]** → 在 spec 中明确单客户端同一时间仅支持一个会话，并要求统一 toast 提示。
- **[跨页面 active 语言不一致]** → 在 global shell 和 settings 两个 capability 中分别定义顶层导航与设置导航的选中约束，避免后续各写各的。

## Migration Plan

1. 先补 proposal、specs、design、tasks，作为本轮 UI polish 的正式记录。
2. 同步更新 `docs/需求文档.md`，将新的 capability 写入 F18-F20，并把 assistant 相关增量写回 F12。
3. 后续如需继续做 Stitch 设计或 archive，可直接基于该 change 继续推进，不需要重新整理聊天记录。

## Open Questions

- 后续是否要把 `llm-chat-ui` 中“单客户端单会话”的限制升级为后端真正支持的多会话并发流。
- 是否要进一步把首页、设置页和助手页的 active 样式提炼成共享组件或统一 token，而不是继续停留在页面级样式约束。
