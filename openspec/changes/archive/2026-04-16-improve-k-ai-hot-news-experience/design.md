## Context

K-Ai 聊天功能已具备热点注入、SSE 流式回复、新闻卡片渲染和会话持久化能力，但当前实现存在三个跨层问题：

1. 前端聊天气泡与状态气泡偏高，热点多条消息时信息密度过低，与 `docs/k-ai-screen.html` 参考稿差距明显。
2. 热点拉取过程通过单条 `agentStatus` 文案反复覆盖，用户无法感知多渠道并行/串行进度，也无法区分开始、成功、跳过和失败。
3. 聊天后端只把热点数据作为“新闻列表生成器”的输入，没有强约束模型继续输出见解和分析；同时启用态过滤散落在 `ChatService`、`FeedService`、`ScraperEngine` 多处，导致已关闭源仍被拉起的风险难以定位。

这次改动同时触达 `renderer/features/assistant/`、`renderer/stores/use-chat-store.js`、`core/chat/`、`main/ipc/chat.handler.js`、`preload/index.js` 与 `core/scraper/`，属于典型的跨层变更，适合先通过 design 锁定事件模型和约束边界。

## Goals / Non-Goals

**Goals:**
- 将热点消息气泡改造成更紧凑的卡片样式，视觉上靠近 `docs/k-ai-screen.html` 的“气泡新闻”区域。
- 将热点拉取过程从“单字符串状态”升级为“可追加的事件流”，支持多渠道逐条展示。
- 在不泄露完整推理历史的前提下，实时展示模型 Thinking 增量片段。
- 调整热点 prompt，使热点请求默认返回“事实 + 见解 + 分析 + 不确定性”，而不是只有新闻列表。
- 明确并收口“disabled source 永不发请求”的系统约束，便于修复 `sputniknewscn` 一类异常。

**Non-Goals:**
- 不引入新的模型提供方，也不更换当前 OpenAI-compatible 调用方式。
- 不做聊天 UI 的整体重设计，仅针对热点卡片、状态流和 Thinking 展示做定向增强。
- 不在本次变更中落地复杂的多轮 reasoning 历史面板或可折叠推理时间线。
- 不调整后台数据源管理页的业务流程，只修正启用态在消费链路中的执行一致性。

## Decisions

### D1. 将聊天流式事件拆分为 `status` / `thinking` / `token`

**选择**: 保留现有 `token` 事件用于最终正文，新增 `thinking` 事件用于模型实时思考增量，`status` 事件专门承载热点拉取阶段的渠道级进度。

**原因**:
- 目前 `agentStatus` 与正文流混在一起，前端只能在“状态”和“正文”之间二选一切换，无法同时保留“拉取轨迹”和“当前思考”。
- Thinking 是瞬时过程，正文是最终回答，两者生命周期不同，分事件后更容易只展示“实时部分，不展示完整历史”。
- 事件语义清晰后，preload 与 store 不必靠字符串格式推断状态类型。

**备选方案**:
- 继续复用 `status` 文本，靠前缀约定区分热点状态与 Thinking。
  放弃原因：字符串协议脆弱，前端难以可靠渲染不同 UI。
- 将 Thinking 混入正文 token。
  放弃原因：会污染最终 assistant 内容，也无法满足“只显示实时部分”。

### D2. 热点拉取状态改为“事件列表追加”，不再覆盖单条文案

**选择**: `ChatService._fetchHotTopics()` 不再只输出 `正在拉取热点...｜xxx拉取成功` 这样的聚合文本，而是为每个源发出独立事件，事件至少包含 `phase`（start/success/skipped/failed）、`sourceId`、`sourceName`、`detail`、`timestamp`。

**原因**:
- 用户明确希望多个渠道 append 追加显示。
- 独立事件便于前端做时间顺序列表，也便于在失败排查时看到具体卡在哪个源。
- 结构化事件可复用在日志埋点和测试断言中。

**备选方案**:
- 仅把聚合文本保存在数组中由前端拆分。
  放弃原因：事件丢失结构化字段，无法准确表达 skipped/disabled 等状态。

### D3. Thinking 仅保留“本轮实时增量缓冲”，完成后默认折叠清空

**选择**: store 中新增单独的 `streamingThinking` 字段，只累积当前进行中的增量片段；收到 `done`、`error` 或 `abort` 后清空该缓冲，不将 Thinking 落库，也不并入最终 assistant message。

**原因**:
- 用户明确要求“只显示实时部分，不要全部显示”。
- 不持久化 Thinking 可以避免会话恢复时重放旧推理内容。
- 与多数模型供应商的 reasoning delta 行为兼容；若接口未返回 reasoning 字段，UI 只是不显示，不会破坏正文。

**备选方案**:
- 将 Thinking 持久化为 assistant message 元数据。
  放弃原因：会引入历史回放与隐私/噪音问题，且超出本次需求。

### D4. Prompt 从“列新闻”升级为“新闻事实 + 见解分析”的双层输出约束

**选择**: 对热点场景的 system prompt 增加明确约束：先基于热点材料提炼关键新闻，再补充趋势、影响、争议点、后续观察项和不确定性说明；除非用户只要列表，否则仅输出新闻条目不算完成。

**原因**:
- 当前 prompt 中存在“请用编号列表格式输出新闻”的强约束，模型容易收敛到纯列表。
- 用户要的是“对新闻的见解、分析”，这属于需求语义变更，必须在 prompt contract 上显式强调。

**备选方案**:
- 只靠前端在用户提问前拼接“请顺便分析”。
  放弃原因：行为不稳定，且对快捷入口、普通热点问题无法统一收口。

### D5. 启用源校验采用“两道门”策略

**选择**:
- 第一层：候选源构建阶段，只从 `sourceRepository.findAll(true)` 取全局启用源，再与 default MCP key 的 `source_scope` 求交集。
- 第二层：任何即将触发网络请求的入口（`refreshOne`、缺缓存补拉、过期同步刷新）都再次查询 DB 启用态；若源已禁用则发出 `skipped` 状态并短路。

**原因**:
- 当前 `ScraperEngine.refreshOne()` 已有单点校验，但 `ChatService`/`FeedService` 等上游仍可能把不该出现的源推进流程，导致日志和 UI 上出现“尝试抓取禁用源”的迹象。
- 双重校验可以兼容 DB 状态在流程中途变化的情况。

**备选方案**:
- 仅保留 `refreshOne()` 内部校验。
  放弃原因：定位问题困难，上游仍会产生误导性的“开始拉取”状态。

### D6. UI 以“紧凑卡片 + 纵向流”的方式承载热点结果和过程

**选择**:
- 热点新闻卡片采用更紧凑的 padding、标题/摘要分层和较短的元信息区，减少每条卡片高度。
- 状态流和 Thinking 均作为 assistant 气泡内部的独立分区出现，而不是额外撑开多个大块容器。

**原因**:
- 用户的核心反馈就是“高度过高，不够美观”。
- 参考稿本身也是“主气泡 + 紧凑分区”的结构，利于在桌面端和窄屏下一致收缩。

## Risks / Trade-offs

- [模型供应商不返回 reasoning delta] → 前端保底只展示正文 token，Thinking 区自动隐藏，不阻塞主流程。
- [事件类型增多导致 preload/store 改动面扩大] → 通过向后兼容的默认分支处理未知事件，并在 spec 中固定事件集合。
- [双重启用态校验引入额外 DB 读取] → 候选源阶段用批量查询，真正请求前仅对将要发请求的单源做二次校验，性能影响可控。
- [更强的分析型 prompt 让回答变长] → 在 prompt 中保留“默认简洁结构化”约束，避免无界扩写。
- [前端持续追加状态事件导致消息区过长] → 限制仅保留当前请求的状态流，结束后可折叠为简短摘要或自然留在本轮气泡中。

## Migration Plan

1. 更新聊天流式协议与 preload 桥接，先支持 `thinking` 与结构化 `status` 事件。
2. 更新 store 和 assistant 页面，接入状态流列表与实时 Thinking 区。
3. 修改 `ChatService` 的热点 prompt 与 `_fetchHotTopics()` 事件发射逻辑。
4. 在热点候选源筛选、缺缓存补拉和 `ScraperEngine.refreshOne()` 前统一加上 enabled guard。
5. 回归测试热点请求、普通聊天、手动中断、禁用源切换后的聊天补拉与定时刷新日志。

**回滚策略**:
- 若 Thinking 事件与模型接口不兼容，可仅回滚 `thinking` 消费逻辑，保留正文流式输出。
- 若结构化状态流影响面过大，可短期退回为顺序文本数组，但仍保留 enabled guard 修复。

## Open Questions

- 当前模型供应商实际返回的 reasoning 字段名是否为 `reasoning_content`、`reasoning` 还是其他别名；实现阶段需要基于真实响应确认。
- 热点状态流在消息完成后是否需要默认折叠为“已拉取 N 个渠道”的摘要，还是保留完整事件列表；本次设计默认保留完整列表。
