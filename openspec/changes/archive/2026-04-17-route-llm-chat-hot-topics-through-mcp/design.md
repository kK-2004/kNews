## Context

当前实现已经把热点来源收口到本地 MCP，但 `ChatService` 仍需要把工具输出再加工成 UI payload，`renderer/features/assistant/index.vue` 展示的热点卡片也只包含标题和 meta，没有每条新闻的一句话说明。与此同时，热点主回答和卡片信息属于两条不同节奏的异步数据流: 一条是原有 llm-chat 主回答流，另一条是更轻量、可逐条完成的新闻摘要补全。

这次变更的重点不是重做 UI，而是在不改动已有新闻卡片样式的前提下，让卡片真正直接消费 MCP JSON，并引入“每条新闻摘要可渐进补齐”的异步能力。设计必须保证：

- 卡片样式、布局和点击交互保持现状；
- 主回答流不等待一句话描述返回；
- 描述请求是批量发起、逐条落位，而不是等全部完成后再一起刷新。

## Goals / Non-Goals

**Goals:**
- 让热点卡片直接基于 MCP JSON 渲染标题、链接、来源、时间等字段，不再依赖文本解析。
- 保持现有热点新闻卡片样式不变，只在标题下补一个可渐进加载的描述区域。
- 使用 `tool_calls` 为每条新闻批量异步生成一句话描述，并与原 llm-chat 主回答流并行执行。
- 让前端在描述未返回时显示加载动画，收到后就地替换，不影响主回答和状态流。
- 保持 K-Ai 页面在流式输出期间可手动回看历史内容，并通过一键到底按钮恢复自动跟随最新行。
- 在不打断当前页面上下文的前提下，为未登录访问 K-Ai 提供轻量登录提示。
- 统一消息时间的展示层级，让当天、当年和跨年的历史消息都具备稳定且易读的时间文案。

**Non-Goals:**
- 不改新闻卡片的现有视觉设计、间距体系或交互模式。
- 不重做热点问答主 prompt 的整体产品策略，只补充摘要并发链路。
- 不要求 MCP Server 负责生成一句话描述；描述生成仍属于聊天编排层。
- 不在本次变更中重做全局登录流程或引入新的认证协议方案。

## Decisions

### D1. 热点卡片以 MCP 结构化 JSON 为单一渲染来源

**选择**: 将聊天热点 payload 定义为稳定的结构化 JSON，对每条新闻至少包含 `id`、`title`、`url`、`sourceId`、`sourceName`、`publishedAt`，前端直接渲染这些字段，不再从 markdown 或 tool 文本中二次解析。

**原因**:
- 结构化 JSON 能把 UI 契约和 prompt 文本解耦，避免后续文案或工具输出格式变化影响卡片渲染。
- 这符合用户“只是改成 MCP JSON 渲染”的要求，也能为单条描述的异步补丁提供稳定定位键。
- 现有卡片 DOM 和样式可以继续复用，只需要在数据层增加 `summary` / `summaryStatus`。

**备选方案**:
- 继续保留 text/markdown 解析，再由前端从文本中提取字段。
  放弃原因：解析脆弱，且不利于增量更新单条新闻描述。

### D2. 一句话描述采用“每条新闻一个异步 tool-call 任务”的后台补全模型

**选择**: 热点数据准备完成后，聊天服务立即启动主 llm-chat 流；同时为每条新闻创建独立的后台摘要任务，使用支持 `tool_calls` 的轻量 LLM 请求生成一句话描述，并以结构化工具参数回传单条结果。

**原因**:
- 每条新闻单独异步执行，最符合“批量异步请求每个新闻的一句话描述”的产品要求。
- 使用 `tool_calls` 返回结构化结果，可以避免再次从自然语言摘要里猜测新闻 id、句子边界或目标位置。
- 任务独立后，单条失败不会拖累其它新闻，也不会阻塞主回答。

**备选方案**:
- 一次请求让模型返回所有新闻摘要。
  放弃原因：任何单条延迟都会拖慢整批结果，也不利于逐条加载动画替换。
- 不使用 `tool_calls`，直接让模型返回普通文本。
  放弃原因：结果更难和具体新闻项稳定绑定。

### D3. 流式协议增加“新闻描述补丁事件”，而不是复用正文 token

**选择**: 在现有 `status` / `thinking` / `token` / `done` 之外，新增面向热点卡片的增量事件类型，用于推送 `{ topicId, summary, state }` 级别的描述补丁。

**原因**:
- 新闻描述和正文 token 属于不同消费路径，拆分事件类型能避免前端 store 混入额外字符串拼接逻辑。
- 前端可以更简单地维护 `pendingHotTopics` 和已落库消息里的热点卡片状态。
- 这也让“描述加载中”与“正文流式中”能够同时存在，而不会相互覆盖。

**备选方案**:
- 把摘要混进正文 token 或 status 文本中。
  放弃原因：前端难以可靠恢复结构化卡片状态，也不利于持久化。

### D4. 现有卡片样式只做插槽式扩展

**选择**: 保留当前热点卡片容器、section、item 和 meta 样式，仅在标题下新增描述插槽；当 `summaryStatus=loading` 时显示小型加载动画，占位高度尽量贴近最终文本。

**原因**:
- 用户明确要求不要改此前的新闻卡片样式。
- 插槽式扩展风险最小，能兼容已完成的视觉迭代和暗色主题覆盖。
- 固定位置加载态能减少布局跳动。

**备选方案**:
- 重构卡片为新组件或重排布局。
  放弃原因：超出需求，且容易引入视觉回归。

### D5. 流式滚动采用“自动贴底可中断”策略

**选择**: 聊天消息区默认自动跟随最新输出；当用户手动向上滚动后，停止自动贴底，并通过一个悬浮的一键到底按钮让用户显式恢复到底部和自动跟随状态。

**原因**:
- 流式长回答如果持续抢夺滚动，会直接破坏用户回看上文和复制内容的体验。
- 用“距离底部阈值”判断是否继续自动贴底，比每次内容变化都强制 `scrollTop = scrollHeight` 更稳。
- 悬浮按钮能让用户在保留历史阅读自由度的同时，快速回到最新生成位置。

**备选方案**:
- 持续强制自动贴底。
  放弃原因：会导致用户无法向上滚动查看历史内容。
- 完全取消自动贴底。
  放弃原因：会让正常使用时的最新内容跟踪体验变差。

### D6. K-Ai 未登录访问在当前页阻止并提示

**选择**: 对 `/assistant` 路由增加登录校验；未登录时取消本次导航，并弹出 warning toast “请登录”，而不是跳转到首页或登录页。

**原因**:
- 用户已经在当前上下文中点击 K-Ai，强制跳转会打断阅读流。
- toast 提示足够轻量，也和现有应用中其他功能的登录提示方式一致。

**备选方案**:
- 重定向到首页或登录页。
  放弃原因：打断感更强，也不符合“访问 K-Ai 不跳转”的明确要求。

## Risks / Trade-offs

- [单次热点问答会额外触发多条摘要请求] → 通过限制单次热点条目数、使用轻量模型与并发上限控制总体成本。
- [部分新闻摘要返回较慢或失败] → 单条失败仅保留加载结束或降级为空，不阻塞主回答和其他条目。
- [新增流式事件会增加前后端状态复杂度] → 用独立事件类型和稳定 `topicId` 做最小增量，避免改动现有正文流逻辑。
- [结构化 JSON 与 UI 字段漂移] → 在 spec 中明确 MCP JSON 的最小字段集合和前端兼容要求。
- [自动贴底状态机不准确] → 用“距底部阈值”与显式一键到底动作同步状态，避免轻微抖动就切换模式。

## Migration Plan

1. 更新 `llm-chat-ui`、`llm-chat-engine` 和 `local-mcp-server` 的 spec，明确 JSON 渲染和摘要补丁行为。
2. 调整聊天热点 payload 结构，让前端直接消费 MCP JSON，并为单条新闻预置 `summaryStatus=loading`。
3. 在聊天编排层引入后台摘要任务，通过 `tool_calls` 并发请求一句话描述，并把结果通过新的流式事件推给前端。
4. 回归验证主回答流、热点状态流、卡片点击交互以及暗色主题样式均保持原有效果。

**回滚策略**:
- 如果后台摘要链路不稳定，可保留 MCP JSON 渲染并暂时关闭一句话描述补全，卡片继续展示标题和 meta，不影响主回答链路。

## Open Questions

- 描述补丁事件是仅更新当前 pending 气泡，还是在最终 assistant message 落库后也需要继续回填已持久化消息；实现阶段需明确持久化策略。
- `tool_calls` 所用模型是否直接复用当前 LLM 配置，还是引入单独的轻量模型配置；本次设计默认复用现有兼容 Chat Completions 的服务，并预留后续拆分空间。
