# kNews Desktop — 软件需求规格说明书 (SRS)

> 版本: 1.0 | 日期: 2026-04-05 | 状态: Draft

---

## 1. 引言

### 1.1 编写目的

本文档定义 kNews Desktop 桌面应用的完整需求，作为开发、测试和验收的依据。面向开发团队、项目管理者及相关利益方。

### 1.2 项目概述

kNews Desktop 是一款**跨平台桌面新闻聚合应用**，聚合 60+ 新闻源，提供本地定时刷新、MCP 协议接入（供 AI 工具调用新闻数据）、双模式登录（GitHub OAuth / Email Magic Link）等能力。支持 Windows 和 Mac 双平台安装包。应用采用缓存优先策略加载数据，减少不必要的网络请求和 UI 闪烁，并提供基于用户等级的功能权限控制。

### 1.3 术语与缩写

| 术语 | 定义 |
|------|------|
| MCP | Model Context Protocol，AI 工具通信协议 |
| Magic Link | 包含登录令牌的邮件链接，用户点击即可完成认证 |
| Deep Link | 自定义 URL 协议（`knews://`），用于从外部唤起应用 |
| IPC | Inter-Process Communication，Electron 进程间通信 |
| Repository | 数据访问层封装模式，隔离 SQL 细节 |
| 策略模式 | 运行时可替换的算法封装模式 |
| 模板方法模式 | 基类定义算法骨架、子类实现具体步骤的设计模式 |
| 缓存优先 | 优先使用本地缓存数据，过期后台静默刷新的加载策略 |

## 2. 总体描述

### 2.1 产品视角

kNews Desktop 是一个**独立的桌面应用产品**，同时对外提供 MCP HTTP 服务接口，供 Claude Desktop、Cursor 等 AI 工具消费新闻数据。

```
┌────────────────────────────────────────────────────────┐
│                   kNews Desktop                         │
│                                                         │
│  ┌─────────────┐  IPC   ┌──────────────────────────┐   │
│  │  Vue 3 前端  │◄──────►│  Electron Main Process   │   │
│  │  (Renderer)  │       │                          │   │
│  │             │       │  ┌─ 认证系统 (OAuth/      │   │
│  │  新闻浏览    │       │  │       Magic Link)     │   │
│  │  源管理      │       │  ├─ 爬虫引擎 (60+源)     │   │
│  │  源管理      │       │  ├─ MCP Server           │───┼──► AI 工具
│  │  用户设置    │       │  └─ 用户管理             │   │
│  └─────────────┘       └──────────┬───────────────┘   │
│                                   │                    │
│                        ┌──────────▼──────────┐        │
│                        │  Supabase PostgreSQL │        │
│                        │  (云端数据库)         │        │
│                        └─────────────────────┘        │
└────────────────────────────────────────────────────────┘
```

### 2.2 用户角色

| 角色 | 描述 | 核心场景 |
|------|------|----------|
| 普通用户 | 桌面端新闻浏览者 | 浏览新闻、管理偏好 |
| API 用户 | 通过 MCP 接入的 AI 工具 | 获取新闻数据、查询可用源 |
| 管理员 | 系统管理者 | 管理源、用户、API Key |

### 2.3 运行环境

| 项目 | 要求 |
|------|------|
| 操作系统 | Windows 10+ 或 macOS 11+ |
| 网络要求 | 首次使用及数据库操作需网络连接 |
| 硬盘空间 | ≥ 200MB |
| 外部服务 | Supabase 云数据库、GitHub OAuth |

## 3. 功能需求

### 3.1 F01 — 桌面应用框架

**描述**: Electron 桌面应用的整体骨架，包括窗口管理、进程通信和打包发布。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F01-01 | 创建 Electron 主窗口，最小宽度 1024px，最小高度 700px | P0 |
| F01-02 | 按领域分组的 IPC 通信层（auth/feeds/sources/scraper/user/mcp/chat），通过 preload contextBridge 安全暴露 | P0 |
| F01-03 | 支持 Windows (NSIS .exe) 和 Mac (.dmg) 安装包打包 | P0 |
| F01-04 | 启动时按序初始化：Supabase 连接 → 数据库建表 → 爬虫启动 → MCP 启动 → Session 恢复 | P0 |
| F01-05 | 关闭窗口时清理所有子系统（定时器、MCP Server） | P0 |

### 3.2 F02 — 认证系统

**描述**: 支持双模式登录（GitHub OAuth / Email Magic Link），采用策略模式 + 工厂模式 + 模板方法模式实现。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F02-01 | AuthTemplate 基类定义认证骨架：initiate → validate → syncUser → createSession | P0 |
| F02-02 | GitHub OAuth 策略：临时 HTTP Server 接收 callback，shell.openExternal 打开浏览器，5 分钟超时 | P0 |
| F02-03 | Email Magic Link 策略：调用 Supabase `signInWithOtp` 发送含登录链接的邮件，用户点击链接完成认证 | P0 |
| F02-04 | 注册 Electron 自定义协议 `knews://`，捕获 `knews://auth/callback?token=xxx` Deep Link 完成登录 | P0 |
| F02-05 | AuthFactory 按 type 字符串创建对应策略实例（`github` / `magic-link`），未知类型抛错 | P0 |
| F02-06 | Session 通过 Electron safeStorage 加密持久化，重启自动恢复 | P0 |
| F02-07 | 登出时清除 Session 并通知前端重置 | P1 |

| F04-06 | Cache 表：id/source_id/data(JSONB)/updated_at | P0 |

### 3.5 F05 — 新闻爬虫引擎

**描述**: 定时抓取 60+ 新闻源，并发控制，缓存管理。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F05-01 | ScraperEngine 定时器，默认 10 分钟刷新全部已启用源 | P0 |
| F05-02 | 支持手动全源刷新和单源刷新 | P0 |
| F05-03 | p-limit 并发控制，最大并发 5，单源超时 30 秒 | P0 |
| F05-04 | SourceFetcher 支持 RSS 解析和 Cheerio HTML 抓取，返回统一格式 (title/url/date/source) | P0 |

| F05-06 | 全局关闭（`enabled = false`）的数据源不得进入任何定时刷新、手动刷新、热点问答补拉或上下文注入链路；系统需在调度前与执行前都进行启用态校验，并记录跳过原因 | P0 |

### 3.6 F06 — 本地 MCP Server

**描述**: 内嵌 HTTP Server，对外提供 MCP 协议服务。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F06-01 | HTTP Server 默认端口 12580，占用时递增，实际端口写入配置 | P0 |
| F06-02 | get_available_sources 工具：返回 API Key 允许访问的源列表 | P0 |
| F06-03 | get_hotest_latest_news 工具：返回可稳定映射为结构化 JSON 的指定源最新新闻，至少覆盖稳定标识、标题、链接、来源和时间字段 | P0 |
| F06-04 | API Key 认证：Authorization Header 验证，更新 last_used/call_count | P0 |
| F06-05 | 频率限制：按 rate_limit 限制每小时请求数，超限返回 429 | P0 |
| F06-06 | 健康检查：GET /mcp/health 返回 status/uptime/port | P1 |

### 3.7 F07 — 缓存优先数据加载

**描述**: 数据加载优先使用文件系统缓存，减少不必要的网络请求和 UI 闪烁，认证状态变化不触发数据重载。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F07-01 | 数据加载时检查每个数据源的缓存状态（是否存在、fetchedAt 时间戳），基于缓存新鲜度决定获取行为 | P0 |
| F07-02 | 所有选中数据源均有缓存且未过期（≤1 小时）时，直接使用缓存数据构建 boards，不显示 loading 骨架屏，不发起新的网络请求 | P0 |
| F07-03 | 部分或全部缓存过期（>1 小时）时，先展示缓存数据，后台静默刷新过期源，刷新完成后无闪烁更新 boards | P0 |
| F07-04 | 无缓存时走正常获取流程，显示 loading 状态，获取完成后写入缓存 | P0 |
| F07-05 | 用户登录/登出（authToken 变化）不触发 `buildBoards()` 全量重建，仅重新加载用户偏好 | P0 |
| F07-06 | 偏好变化影响 boards（如关注列表变化）时，由偏好 watcher 自身触发数据更新 | P1 |
