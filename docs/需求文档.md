# kNews Desktop — 软件需求规格说明书 (SRS)

> 版本: 1.0 | 日期: 2026-04-05 | 状态: Draft

---

## 1. 引言

### 1.1 编写目的

本文档定义 kNews Desktop 桌面应用的完整需求，作为开发、测试和验收的依据。面向开发团队、项目管理者及相关利益方。

### 1.2 项目概述

kNews Desktop 是一款**跨平台桌面新闻聚合应用**，聚合 60+ 新闻源，提供本地定时刷新、MCP 协议接入（供 AI 工具调用新闻数据）、双模式登录（GitHub OAuth / Email Magic Link）等能力。支持 Windows 和 Mac 双平台安装包。应用采用缓存优先策略加载数据，减少不必要的网络请求和 UI 闪烁，并提供基于用户等级的功能权限控制。

### 1.3 术语与缩写

| 术语 | 定义 |
|------|------|
| MCP | Model Context Protocol，AI 工具通信协议 |
| Magic Link | 包含登录令牌的邮件链接，用户点击即可完成认证 |
| Deep Link | 自定义 URL 协议（`knews://`），用于从外部唤起应用 |
| IPC | Inter-Process Communication，Electron 进程间通信 |
| Repository | 数据访问层封装模式，隔离 SQL 细节 |
| 策略模式 | 运行时可替换的算法封装模式 |
| 模板方法模式 | 基类定义算法骨架、子类实现具体步骤的设计模式 |
| 缓存优先 | 优先使用本地缓存数据，过期后台静默刷新的加载策略 |

## 2. 总体描述

### 2.1 产品视角

kNews Desktop 是一个**独立的桌面应用产品**，同时对外提供 MCP HTTP 服务接口，供 Claude Desktop、Cursor 等 AI 工具消费新闻数据。

```
┌────────────────────────────────────────────────────────┐
│                   kNews Desktop                         │
│                                                         │
│  ┌─────────────┐  IPC   ┌──────────────────────────┐   │
│  │  Vue 3 前端  │◄──────►│  Electron Main Process   │   │
│  │  (Renderer)  │       │                          │   │
│  │             │       │  ┌─ 认证系统 (OAuth/      │   │
│  │  新闻浏览    │       │  │       Magic Link)     │   │
│  │  源管理      │       │  ├─ 爬虫引擎 (60+源)     │   │
│  │  源管理      │       │  ├─ MCP Server           │───┼──► AI 工具
│  │  用户设置    │       │  └─ 用户管理             │   │
│  └─────────────┘       └──────────┬───────────────┘   │
│                                   │                    │
│                        ┌──────────▼──────────┐        │
│                        │  Supabase PostgreSQL │        │
│                        │  (云端数据库)         │        │
│                        └─────────────────────┘        │
└────────────────────────────────────────────────────────┘
```

### 2.2 用户角色

| 角色 | 描述 | 核心场景 |
|------|------|----------|
| 普通用户 | 桌面端新闻浏览者 | 浏览新闻、管理偏好 |
| API 用户 | 通过 MCP 接入的 AI 工具 | 获取新闻数据、查询可用源 |
| 管理员 | 系统管理者 | 管理源、用户、API Key |

### 2.3 运行环境

| 项目 | 要求 |
|------|------|
| 操作系统 | Windows 10+ 或 macOS 11+ |
| 网络要求 | 首次使用及数据库操作需网络连接 |
| 硬盘空间 | ≥ 200MB |
| 外部服务 | Supabase 云数据库、GitHub OAuth |

## 3. 功能需求

### 3.1 F01 — 桌面应用框架

**描述**: Electron 桌面应用的整体骨架，包括窗口管理、进程通信和打包发布。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F01-01 | 创建 Electron 主窗口，最小宽度 1024px，最小高度 700px | P0 |
| F01-02 | 按领域分组的 IPC 通信层（auth/feeds/sources/scraper/user/mcp），通过 preload contextBridge 安全暴露 | P0 |
| F01-03 | 支持 Windows (NSIS .exe) 和 Mac (.dmg) 安装包打包 | P0 |
| F01-04 | 启动时按序初始化：Supabase 连接 → 数据库建表 → 爬虫启动 → MCP 启动 → Session 恢复 | P0 |
| F01-05 | 关闭窗口时清理所有子系统（定时器、MCP Server） | P0 |

### 3.2 F02 — 认证系统

**描述**: 支持双模式登录（GitHub OAuth / Email Magic Link），采用策略模式 + 工厂模式 + 模板方法模式实现。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F02-01 | AuthTemplate 基类定义认证骨架：initiate → validate → syncUser → createSession | P0 |
| F02-02 | GitHub OAuth 策略：临时 HTTP Server 接收 callback，shell.openExternal 打开浏览器，5 分钟超时 | P0 |
| F02-03 | Email Magic Link 策略：调用 Supabase `signInWithOtp` 发送含登录链接的邮件，用户点击链接完成认证 | P0 |
| F02-04 | 注册 Electron 自定义协议 `knews://`，捕获 `knews://auth/callback?token=xxx` Deep Link 完成登录 | P0 |
| F02-05 | AuthFactory 按 type 字符串创建对应策略实例（`github` / `magic-link`），未知类型抛错 | P0 |
| F02-06 | Session 通过 Electron safeStorage 加密持久化，重启自动恢复 | P0 |
| F02-07 | 登出时清除 Session 并通知前端重置 | P1 |

### 3.2.1 F02-A — 登录模态框

**描述**: 独立的登录模态框组件，整合 Magic Link 和 GitHub 两种登录方式，替代旧的 popover 内嵌 OTP 表单。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F02-A-01 | 未登录时 header 右侧显示"登录"文字按钮（替代 GitHub 图标圆形按钮），已登录显示用户头像 | P0 |
| F02-A-02 | 模态框布局参照设计稿，包含：标题"安全访问"、邮箱输入 + "发送验证码"渐变按钮、分割线、GitHub 登录按钮、底部隐私链接 | P0 |
| F02-A-03 | 模态框支持点击遮罩区域或 Escape 键关闭，带淡入淡出过渡动画 | P0 |
| F02-A-04 | Magic Link 流程：输入邮箱 → 调用 IPC `sendMagicLink` → 显示"请查收邮件"状态 → 支持 Deep Link 回调自动关闭模态框 | P0 |
| F02-A-05 | GitHub 登录按钮关闭模态框后触发 GitHub Device Flow（复用现有 `github-device-dialog`） | P0 |
| F02-A-06 | 登录后头像按登录类型显示：GitHub 用户显示 GitHub 头像，邮箱用户显示 `i-tabler-user` 图标 | P1 |

### 3.3 F03 — 用户管理

**描述**: 用户生命周期管理，首次登录自动创建，信息同步更新。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F03-01 | 用户表：id(BIGINT IDENTITY)/email/github_id/nickname/level/balance/created_at/updated_at | P0 |
| F03-02 | GitHub 首次登录按 github_id 查找或创建用户 | P0 |
| F03-03 | Email (Magic Link) 首次登录按 email 查找或创建用户（nickname 取邮箱前缀） | P0 |
| F03-04 | 重复登录更新 updated_at，GitHub 信息变更时同步 nickname | P0 |

### 3.4 F04 — 数据库层

**描述**: 基于 Supabase PostgreSQL 的数据存储，采用 Repository 模式封装数据访问。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F04-01 | Supabase 客户端全局单例，环境变量配置 | P0 |
| F04-02 | 幂等 SQL 迁移脚本，按序创建 users/api_key/source/cache/preference 五张表 | P0 |
| F04-03 | 每个 Repository class 封装表的 CRUD，构造函数注入 Supabase 客户端 | P0 |
| F04-04 | API Key 表：id/user_id/key_hash/name/is_active/source_scope/rate_limit/max_count/last_used/call_count | P0 |
| F04-05 | Source 表：id/name/url/category/enabled/config | P0 |
| F04-06 | Cache 表：id/source_id/data(JSONB)/updated_at | P0 |
| F04-07 | Preference 表：id/user_id/data(JSONB)/updated_at | P1 |

### 3.5 F05 — 新闻爬虫引擎

**描述**: 定时抓取 60+ 新闻源，并发控制，缓存管理。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F05-01 | ScraperEngine 定时器，默认 10 分钟刷新全部已启用源 | P0 |
| F05-02 | 支持手动全源刷新和单源刷新 | P0 |
| F05-03 | p-limit 并发控制，最大并发 5，单源超时 30 秒 | P0 |
| F05-04 | SourceFetcher 支持 RSS 解析和 Cheerio HTML 抓取，返回统一格式 (title/url/date/source) | P0 |
| F05-05 | 成功写入 Supabase cache 表，失败保留上次缓存并记录日志 | P0 |

### 3.6 F06 — 本地 MCP Server

**描述**: 内嵌 HTTP Server，对外提供 MCP 协议服务。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F06-01 | HTTP Server 默认端口 12580，占用时递增，实际端口写入配置 | P0 |
| F06-02 | get_available_sources 工具：返回 API Key 允许访问的源列表 | P0 |
| F06-03 | get_hotest_latest_news 工具：从缓存返回指定源最新新闻 | P0 |
| F06-04 | API Key 认证：Authorization Header 验证，更新 last_used/call_count | P0 |
| F06-05 | 频率限制：按 rate_limit 限制每小时请求数，超限返回 429 | P0 |
| F06-06 | 健康检查：GET /mcp/health 返回 status/uptime/port | P1 |

### 3.7 F07 — 缓存优先数据加载

**描述**: 数据加载优先使用文件系统缓存，减少不必要的网络请求和 UI 闪烁，认证状态变化不触发数据重载。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F07-01 | 数据加载时检查每个数据源的缓存状态（是否存在、fetchedAt 时间戳），基于缓存新鲜度决定获取行为 | P0 |
| F07-02 | 所有选中数据源均有缓存且未过期（≤1 小时）时，直接使用缓存数据构建 boards，不显示 loading 骨架屏，不发起新的网络请求 | P0 |
| F07-03 | 部分或全部缓存过期（>1 小时）时，先展示缓存数据，后台静默刷新过期源，刷新完成后无闪烁更新 boards | P0 |
| F07-04 | 无缓存时走正常获取流程，显示 loading 状态，获取完成后写入缓存 | P0 |
| F07-05 | 用户登录/登出（authToken 变化）不触发 `buildBoards()` 全量重建，仅重新加载用户偏好 | P0 |
| F07-06 | 偏好变化影响 boards（如关注列表变化）时，由偏好 watcher 自身触发数据更新 | P1 |

### 3.8 F08 — 手动刷新权限控制

**描述**: 手动"一键刷新"按钮基于用户等级进行权限控制。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F08-01 | 手动刷新按钮仅对已登录且 `user.level >= 1` 的用户可见和可用 | P0 |
| F08-02 | 已登录但 level < 1 的用户点击刷新时，显示升级订阅提示（toast 通知），同时导航到订阅页面（F09） | P1 |
| F08-03 | 未登录用户显示刷新按钮，点击时 toast 提示"请先登录" | P1 |

### 3.9 F09 — 订阅页面

**描述**: 独立的三级定价订阅页面，参照 `docs/subscribe.html` 设计稿，支持用户查看和选择方案。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F09-01 | 订阅页面展示三级定价卡（Free 0 元 / Plus 5 元月 / Pro 15 元月），每卡包含方案名称、价格、功能列表、操作按钮 | P0 |
| F09-02 | 当前方案及所有低级方案卡片高亮并禁用操作按钮；当前方案显示"当前方案"，低级方案显示"已包含" | P0 |
| F09-03 | 未登录用户点击升级按钮提示先登录 | P0 |
| F09-04 | Free 方案功能列表：3 次 MCP 请求/小时、基础新闻浏览、受限 API 访问 | P0 |
| F09-05 | Plus 方案功能列表：100 次 MCP 请求/小时、一键手动刷新、邮件支持；Plus 卡片显示"最受欢迎"标签 | P0 |
| F09-06 | Pro 方案功能列表：不限次数 MCP 请求、优先 API 路由、专属客户管理、自定义安全协议 | P0 |
| F09-07 | 用户菜单 popover 新增"订阅方案"入口，附带当前方案标签（Free/Plus/Pro） | P0 |
| F09-08 | 升级确认对话框：显示目标方案名称和价格，确认按钮点击后进入 loading 状态（3s），完成后显示成功反馈 | P0 |
| F09-09 | 升级成功后更新 userStore.profile.level，刷新订阅页面当前方案高亮 | P0 |

### 3.10 F10 — 订阅管理（后端）

**描述**: 后端订阅管理，包括 subscriptions 表、SubscriptionRepository、SubscriptionService 及 IPC 通道。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F10-01 | Subscriptions 表：id(TEXT PK)/user_id(BIGINT FK)/plan('free'/'plus'/'pro')/level(0/1/2)/status('active'/'expired')/started_at/expires_at/created_at/updated_at | P0 |
| F10-02 | SubscriptionRepository：findActiveByUserId、create、expireById 方法 | P0 |
| F10-03 | SubscriptionService.createSubscription：旧订阅标记 expired → 模拟支付(3s) → 创建新订阅 → 更新 users.level → 同步 MCP API Key 权限 | P0 |
| F10-04 | SubscriptionService.getCurrentSubscription：返回当前有效订阅，无则返回 Free 默认信息 | P0 |
| F10-05 | Level 与 MCP 权限映射：level 0 → rate_limit=3/max_count=10；level 1 → rate_limit=100/max_count=50；level 2 → rate_limit=-1/max_count=-1 | P0 |
| F10-06 | 防止重复订阅：用户已有 active 相同 plan 订阅时返回当前订阅，不创建新记录 | P1 |
| F10-07 | IPC 通道 subscription:getCurrent：返回当前用户订阅信息 | P0 |
| F10-08 | IPC 通道 subscription:create：执行模拟支付(3s)后创建订阅并返回结果 | P0 |

### 3.11 F11 — 模拟支付

**描述**: 使用 setTimeout 模拟支付流程，封装为独立 PaymentService 以便后续替换为真实支付网关。

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F11-01 | PaymentService.processPayment：setTimeout 3000ms 模拟延迟，返回 `{ success: true, transactionId }` | P0 |
| F11-02 | 支付进行中前端确认按钮显示 loading 状态（"处理中..."），禁止重复点击 | P0 |
| F11-03 | 支付成功后前端更新 userStore.profile.level，关闭对话框，显示成功 toast | P0 |
| F11-04 | PaymentService 接口抽象为独立模块，后续可替换为真实支付网关无需改动调用方 | P1 |

## 5. 约束

| 编号 | 约束内容 |

| C01 | 首次使用需网络连接，本期不做离线模式 |
| C02 | 本期不做自动更新功能 |
