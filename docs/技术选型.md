# 技术选型

## GitHub 认证：Device Flow vs OAuth Authorization Code Flow

**选择：GitHub Device Flow**

### 方案对比

| | Device Flow | OAuth + Deep Link |
|---|---|---|
| UX | 用户手动复制验证码到浏览器 | 点击授权后自动跳回应用 |
| client_secret | 不需要 | 需要嵌入客户端，可被反编译提取 |
| 实现复杂度 | 低 | 中（需要 deep link 回调 + code 换 token） |
| 适用场景 | CLI / 桌面应用 | Web 应用 |

### 选择理由

1. **安全性**：Device Flow 不需要 `client_secret`，避免将密钥编译进桌面客户端二进制文件。虽然 VS Code 等应用确实嵌入了 `client_secret`，但这属于已知风险——任何用户都可以反编译提取
2. **实现简洁**：无需 deep link 回调处理授权码交换，整个流程只需 `initiate → poll → done` 三步
3. **GitHub 官方推荐**：GitHub 明确推荐桌面应用和 CLI 工具使用 Device Flow

### 可选迁移路径

项目已注册 `knews://` 自定义协议（Magic Link 在用）。如果未来 Device Flow 的 UX（复制验证码、手动切回应用）成为用户痛点，可以迁移到 OAuth Authorization Code Flow：

- GitHub OAuth App 添加 `knews://auth/callback` redirect URI
- `initiate` 改为拼接授权 URL（而非请求 device code）
- `validate` 通过 deep link 接收 code 换 token
- 授权完成后由 deep link 自动唤起应用，无需手动切换
