## 1. 开发模型选型

### 1.1 候选模型分析

| 模型 | 适用场景 | 与本项目的匹配度 |
|------|----------|-----------------|
| **瀑布模型** | 需求完全明确、变更少 | 中 — 需求已明确，但无法做到"全部做完再测试"，桌面打包等环节需尽早验证 |
| **增量模型** | 可拆分独立模块、分批交付 | **高** — 系统天然可拆为数据库→后端→前端→MCP 等独立增量 |
| **螺旋模型** | 技术风险高、需原型验证 | 低 — 技术栈已确定（Electron + Supabase），无重大技术风险 |
| **敏捷 Scrum** | 需求频繁变更、用户反馈驱动 | 中低 — 需求已锁定，不需要短迭代频繁调整方向 |
| **V 模型** | 强调测试、安全关键系统 | 低 — 非安全关键系统，测试粒度可灵活调整 |
| **原型模型** | 需求不明确、需 UI 验证 | 低 — 需求已通过 spec 详细定义 |

### 1.2 选定模型：增量模型（Incremental Model）

**理由**:

1. **需求明确**：所有功能需求已通过 proposal、design、specs 详细定义，无需探索
2. **模块天然独立**：数据库、后端业务层、认证系统、爬虫引擎、MCP Server、前端适配——每个模块可独立开发和验证
3. **风险前置**：先完成底层数据库和核心后端，再构建上层功能，问题能在早期暴露
4. **持续可验证**：每个增量完成后都能独立运行和测试，不必等全部开发完
5. **资源适配**：适合小团队，可按模块分配给不同角色并行推进

### 1.3 增量划分策略

采用**自底向上**的增量顺序：先基础设施（数据库），再核心业务（后端），最后集成（前端 + 打包）。

```
增量1: 项目骨架 + 数据库层       → 可运行空壳 + 数据库可连接建表
增量2: 后端业务层（OOP）         → Service/Repository 可单元测试
增量3: 认证系统                  → 可完成 GitHub OAuth / Email OTP 登录
增量4: 爬虫引擎                  → 可定时抓取新闻并缓存
增量5: MCP Server               → 外部 AI 工具可调用新闻数据
增量6: 前端适配 + Electron 集成  → 完整桌面应用可使用
增量7: 打包发布 + 集成测试       → 生成安装包并通过验收测试
```

## 2. 团队角色与分工

### 2.1 角色定义

| 角色 | 职责范围 | 负责目录 |
|------|----------|----------|
| **数据库开发 (DB)** | Supabase 建表、SQL 迁移、数据访问层 (Repository) | `database/` |
| **后端开发 (BE)** | 业务逻辑 (Service)、认证系统、爬虫引擎、MCP Server、IPC Handler | `core/`, `main/` |
| **前端开发 (FE)** | Vue 3 页面、IPC API 适配、Supabase OTP 前端流程 | `renderer/`, `preload/` |
| **集成/DevOps (INT)** | Electron 打包配置、启动引导流程、环境配置 | `config/`, 根目录配置文件 |

> 注：本团队为小团队，角色可由同一人兼任，但职责划分保持清晰。

## 4. 并行开发策略

各增量内可并行的任务：

```
增量1:  INT(骨架) ─────┐
        DB(数据库) ─────┤──→ 汇合验证
        FE(preload) ────┘

增量2:  DB(4个Repository) ──┐      ← 可同时开发4个Repo
        BE(3个Service) ──────┤──→ 汇合验证

增量3:  BE(认证系统5个文件) ──┐
        FE(OTP前端) ────────────┤──→ 联调

增量4:  BE(SourceFetcher) ──┐
        BE(源适配) ─────────────┤──→ 汇合
        BE(ScraperEngine) ─────┘

增量5:  BE(McpServer) ─────┐
        BE(工具+认证) ────────┤──→ 汇合

增量6:  FE(6个API适配) ─────┐      ← 前端6个文件可同时改
        BE(5个IPC Handler) ──┤──→ 联调
        BE(Bootstrap) ────────┘

增量7:  INT(Mac打包) ──────┐
        INT(Win打包) ────────┤──→ 验收
        BE(集成测试) ─────────┘
```

## 5. 技术决策记录

| 编号 | 决策 | 选择 | 理由 |
|------|------|------|------|
| TD01 | 桌面框架 | Electron | 跨平台成熟方案，前端 Vue 3 可复用 |
| TD02 | 数据库 | Supabase PostgreSQL | 云端托管，自带 Auth SDK 用于 OTP |
| TD03 | 进程通信 | Electron IPC (invoke/handle) | 官方推荐安全模式，天然支持 Promise |
| TD04 | 认证架构 | 策略+工厂+模板方法 | 可扩展、共用逻辑复用、调用方解耦 |
| TD05 | 并发控制 | p-limit | 轻量，控制抓取并发数 |
| TD06 | JWT 验证 | jose | 纯 JS 实现，无 Node 原生依赖，Electron 兼容好 |
| TD07 | OOP 分层 | main → core → database | 单向依赖，core 不依赖 Electron 可独立测试 |
